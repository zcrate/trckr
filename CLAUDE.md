# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Toolchain is Python 3.14 + `uv`. `pyproject.toml` declares no runtime dependencies; `pytest`
is in the `dev` dependency group. The project builds with hatchling so that `uv sync`
installs the `trckr` console script (entry point `src.main:main`).

```bash
uv sync                                                 # one-time setup (.venv is gitignored)
uv run python -m pytest                                 # run all tests
uv run python -m pytest tests/test_cli.py               # one file
uv run python -m pytest tests/test_engine.py::test_process_trigger_auto_stop_grouped_timer  # one test
uv run trckr --help                                     # the CLI
```

Always run pytest from the repo root with `python -m pytest`, not bare `pytest`. Tests and
modules import via the `src.` package path (`from src.core.engine import ...`), which only
resolves when the repo root is on `sys.path`.

`src/main.py` is the argparse CLI (`add`, `group add|list`, `trigger`, `status [--json]`,
`log`, `tag set|list`). It is the only place that wires the engine to storage. Global
`--data-dir` (or env `TRCKR_DATA_DIR`) selects the data directory; default is `data`. Items
and groups get `itm_`/`grp_` plus 8 random hex chars and can be referenced by id or by
case-insensitive label. User errors raise `CLIError`, printed to stderr with exit code 1.
`tests/test_cli.py` drives `main([...])` directly against a `tmp_path` data dir.

## Core concept

Every user action is reduced to an append-only stream of immutable, timestamped **events**. There
is no stored "current state": item states, running timers, and counts are derived by replaying the
event log. Keep this invariant when adding features. Never mutate or delete events; emit new ones.

## Architecture

Three layers, deliberately decoupled. The engine is pure functions over plain dicts and never
touches storage; the caller wires them together.

- **`src/core/engine.py`**: the state engine.
  - `resolve_item_state(item_id, events)` filters and sorts the log for one item and returns
    `event_count`, `is_active` (odd count = running), and `last_timestamp`. It does not look at
    `action`, so it works for `toggle`-only clients.
  - `process_trigger(item, all_items, events, timestamp, source)` is the ingestion rule. It does
    **not** write anything; it returns the list of new events to append. For a `timed` item with a
    `group_id` it first emits an `auto_group` `stop` event (same `timestamp`) for every running
    sibling in the group, then the item's own event (`count` for counted items, else `start`/`stop`
    based on current parity). Auto-stop events come first in the returned list; tests rely on that.
  - `resolve_item_duration(item_id, events, now)` pairs an item's sorted events
    (even index opens, odd index closes) and returns `total_seconds`, `current_seconds`
    (the open interval measured to `now`), and `is_active`. Used by `trckr status`.
  - `enrich_item_tags(item, tag_registry)` resolves item tag strings against the tag registry and
    synthesizes `{id, label, color, icon}` with a `get_auto_color` fallback for unregistered tags.
    Note: the synthesized dict includes `label`, which `schemas/tag.json` does not allow; enriched
    tags are a view-model, not something to persist.
- **`src/core/utils.py`**: tag string handling. `normalize_tag` (NFC, lowercase, trim, collapse
  whitespace) is the canonical storage form; `normalize_tags` also dedupes and sorts;
  `slugify_tag` produces an underscore-joined, hyphen-preserving slug for URLs/CLI;
  `get_auto_color` hashes the normalized tag into a fixed 12-color `PALETTE`, so colors are
  deterministic and case-insensitive.
- **`src/storage/json_db.py`**: `JSONStorage` persists four flat JSON arrays in `data/`
  (`groups.json`, `tags.json`, `items.json`, `events.json`), creating the directory and empty
  files on construction. `append_events` is the only event write path and only appends.
  `save_tag` upserts by `id`; `save_item` and `save_group` append blindly. The default `DATA_DIR`
  is the relative path `data`, so storage location depends on the working directory. `data/` is
  gitignored.

Event IDs generated by `process_trigger` are `evt_<uuid4 hex>` / `evt_auto_<uuid4 hex>`.
Tests only assert the prefixes.

## Data model (`schemas/`, JSON Schema draft-07, `additionalProperties: false`)

| Schema | ID prefix | Purpose |
|---|---|---|
| `event.json` | `evt_` | Log entry: `item_id`, `timestamp` (ISO-8601 UTC), optional `action` (`start`/`stop`/`count`/`toggle`), optional `source` (`widget`, `manual_tap`, `auto_group`, `sensor`, ...). |
| `item.json` | `itm_` | Tracked template. `type` is `timed` or `counted`. Optional `group_id` (nullable) and `tags` (array of strings, max 30 chars each). |
| `group.json` | `grp_` | Mutual-exclusion category for timed items. |
| `tag.json` | none (plain string, max 30) | Visual metadata only (`color` hex, optional `icon`). Lives in `data/tags.json`. Does not affect event logic. |

Item `tags` are plain strings that match a `tag.json` `id`; the registry has no `label` field
(removed deliberately in commit d221cbf). Nothing currently validates dicts against these schemas
at runtime; the schemas are the contract, and the engine trusts its inputs.

ID patterns are enforced by regex (`^evt_[a-zA-Z0-9_-]+$` etc.). Any new entity should follow the
same `<prefix>_` convention and set `additionalProperties: false`.
